# Galaxy Buds On for GalaxyBudsClient (macOS)

This repository builds an Apple Silicon version of [GalaxyBudsClient](https://github.com/timschneeb/GalaxyBudsClient) for Galaxy Buds On (SM-U600). The app uses the Samsung management channel for device status and specific confirmed setting commands.

## Install

The [hardware-checked Apple Silicon build](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45736098878/artifacts/15079720347) is the current baseline. It confirmed an EQ change on SM-U600 and read the new preset again after reconnecting. Download the artifact, unzip it, and open the included `.pkg`. If the artifact expires, use the workflow for [the baseline build](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45736098878) as the build reference. macOS may ask you to approve this unsigned installer. The build runs in GitHub Actions and requires no local Xcode or App Store sign-in.

The workflow checks out upstream commit `85dfc8bb39fc45d3c30ecf71ab2c663fb1d41729`, applies `add_buds_on.py`, and builds the native Bluetooth library and app with the pinned cloud toolchain.

## Experimental Mac audio handoff

Preview 2 is version **5.2.1.2**. Quit the running app after installing, then reopen it. Settings displays **Buds On handoff preview 2**. This build fixes an empty-control accessibility crash in its pinned FluentAvalonia dependency. The cloud build verifies empty and populated accessibility peers alongside the Bluetooth transport tests.

[Download the Apple Silicon handoff preview](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45893008917/artifacts/15152283106), unzip it and open `GalaxyBudsOn-Handoff-Preview-macOS-arm64.pkg`. The [GitHub Actions build](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45893008917) passed the simulated transport tests and verified the arm64 app and native entry points inside the installer. The [experimental branch](https://github.com/matt-gummow/galaxy-buds-on-preview/tree/experimental/buds-on-mac-handoff) contains the code and workflow.

A saved SM-U600 Galaxy Book capture shows the Book sending one computer audio handoff request on the Samsung SMEP service, 2.216 seconds after reconnecting. The frame matched the clear-flag `0x71` layout and passed its checksum. The recording does not reveal whether the Buds accepted it or whether the Fold stayed connected. Earlier settings and version messages have unverified fields on this model.

On the experimental branch, **Settings → Experimental audio handoff** can open the SMEP control channel to the currently connected Buds. Start with music playing from the Fold. If connecting the Mac already interrupts it, stop there. If the Fold keeps playing, choose **Prepare handoff test**. If it stops during preparation, record that result in the panel. If it keeps playing, confirm you can still hear the Fold and choose **Request Mac audio once**. Report what you hear, including whether a short sound from the Mac plays through the Buds. The connection report records the test stages and the Mac's default output when available. Application-specific output routing can differ.

The experiment sends only the observed audio request, after explicit confirmation, and closes its temporary channel. Read-only diagnostics disables it. Firmware operations and the Book's unverified settings and version writes remain blocked.

## Using the app

| Page | Buds On support |
| --- | --- |
| **Home** | Left earbud, right earbud, and case battery from validated device status. The app groups matching earbud percentages and uses the macOS headset battery when available while waiting for device status. |
| **Touchpad** | Media controls, Answer call or end call, and Decline call. These commands were confirmed on SM-U600 in the preceding hardware previews. Left and right volume hold are available for experimental testing when both hold actions are known. |
| **Equalizer** | Six standard presets from Balanced through Treble boost. Preset writes passed a hardware test in the previous preview. A Custom curve can be read from the device when it returns a supported reply. Custom curve editing remains disabled. |
| **Settings** | Experimental Gaming mode and Pause when one earbud is removed, a reversible read-only mode for the running app, and the connection report. |

Pair the earbuds in macOS Bluetooth first and connect in GalaxyBudsClient. Changes are explicit actions on the selected device. The app checks recent status before sending a change. A matching EQ reply updates the preset without reconnecting. If the earbuds only acknowledge a touch command, select **Refresh status** to check the result. Last reported values stay visible during a management reconnect, and they do not authorize writes. The app sends each setting command once.

Volume hold changes only the selected earbud and preserves the other side. This build supports the Off and Volume values. Actions assigned to an assistant or another behavior require using the phone. A mixed media control state is displayed as unavailable for editing. Active Custom EQ is protected from replacement.

## Connection and multipoint

Open **Settings → Copy Buds On connection report** after connecting or attempting a connection. The same report is saved to `~/Library/Application Support/GalaxyBudsClient/buds-on-connection-report.txt`. It omits Bluetooth addresses and packet dumps.

The report summarizes complete 8-byte `0x76` multipoint notices. It includes the firmware’s support flag, connection state, audio focus, and known streaming profiles. The final three unverified payload bytes are omitted. An earlier SM-U600 report showed the firmware support flag and a multiple-device state. The subsequent simultaneous Galaxy phone and Mac connection attempt failed. That report showed a one-device state with the support flag still set. The current preview supports using one of those audio hosts at a time. Samsung documents Auto Switch for compatible Galaxy devices and Windows PCs running Galaxy Connect. [Samsung Galaxy Buds On](https://www.samsung.com/us/audio-sound/galaxy-buds-on/)

In a Galaxy Book and Galaxy phone test, the listener heard audio switch to the phone and back. During the same recording, the Book requested a disconnect of its classic Bluetooth link to the Buds and reconnected 4.82 seconds after the controller reported the disconnect. The recording covers only the Book and contains no call markers. Whether the phone and Book held simultaneous audio connections during the call is still unknown.

Service discovery identified Samsung’s SMEP service. The Book sent an extended `MDE_VERSION` message 0.685 seconds after reconnecting. The Buds returned a notification with the MDE property header 0.831 seconds later. Whether it echoes the sent version on SM-U600 is unverified. The extended message contains additional fields whose purpose on SM-U600 is unknown. In its initial pass, the reader recognized no multipoint command or status report in either interval and found no classic media channel opening (AVDTP) or classic call-audio connection (SCO/eSCO). The recording had incomplete records and the reader did not cover LE Audio. The Fold’s link was outside the capture. This result leaves concurrent audio connections and compatibility with the upstream version-only write unverified.

A read-only rescan of the same Galaxy Book recording checked the two Buds4 Pro computer handoff encodings in the original reference. Its vendor-channel matcher required a set header flag. It found zero matches on the regular or vendor service, zero matches on unidentified services, and no matching host transport announcement. The second connection interval contained six checksum-verified Samsung vendor frames, including the extended version message and the subsequent notification. Thirteen incomplete or unusable ACL records across the capture and the absence of LE Audio coverage limited the original search. A later pass recognized the clear-flag request in that interval. [Reference implementation](https://github.com/hoshsadiq/buds4-pro-poc/tree/be75d186314ed91fd078c549cd22befd8b639856)

In a separate synchronized Galaxy Book and Fold test, Windows reported the Buds connected immediately before and after all 153 Android profile reads over a 58.9-second run. Android reported both the media (A2DP) and call (HFP) profiles connected to the same Buds on every read. Windows used its cached classic connection flag. The controller scan completed without a reported gap but did not capture an initial connection for the Buds, so it could not establish continuous controller-level connectivity. The listener confirmed that the Fold call came through the Buds and that the Book’s music resumed after hang-up without any Bluetooth interaction. This verifies automatic call switching and return for this Galaxy Book and Fold. The recording had no timestamped listener markers or active audio route readings, so the exact handoff times remain unknown.

In a synchronized Mac and Fold test, the Fold started with both media (A2DP) and call (HFP) profiles connected and music playing through the Buds. The Mac reported a connection event at 19.05 seconds. By 20.13 seconds the Fold reported both profiles disconnected. At 20.29 seconds macOS showed the Buds as its audio output, and the listener confirmed hearing Mac music. Both Fold profiles stayed disconnected through the last read at 32.79 seconds. This run verified a manual handoff. The recorder skipped the call because both Fold profiles had dropped. The Mac’s polled classic connection flag disagreed with its connection event and audio route, so brief overlap at the Bluetooth link level remains unresolved.

In a separate preview 2 test on SM-U600, Fold music was audible through the Buds until the Mac app reconnected its management session. The listener reported that playback stopped at reconnect, before **Prepare handoff test** or **Request Mac audio once**. This run ended there. It had no synchronized Fold profile readings. A remaining question is whether macOS can open the Buds’ Samsung control service directly while Fold playback continues.

Samsung names Galaxy Connect 4.6.13xx.0 or later for Buds On switching on compatible non-Galaxy Windows PCs. Microsoft’s catalog lists Galaxy Connect under the Samsung Continuity Service package family. Version 4.6.1327.0 declares services for continuity handoff and remote media. These declarations identify software to investigate, but they do not say which service ran during the Galaxy Book recording. [Samsung’s SM-U600 specification](https://www.samsung.com/sec/buds/galaxy-buds-on-u600/SM-U600NZKAKOO/) · [Windows catalog check](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45768572934)

Samsung documents that nearby hosts exchange earbud connection information over Bluetooth Low Energy for the original Galaxy Buds Pro. Its Android Continuity Service also lists call- and media-triggered Buds switching. This makes coordination between the Book and the phone a candidate for SM-U600. The saved recording examined the Book’s classic link to the earbuds and did not establish whether either host exchanged such messages. [Samsung’s Auto Switch description](https://www.samsungsvc.co.kr/solution/83885) · [Android Continuity Service](https://galaxystore.samsung.com/detail/com.samsung.android.mcfds)

Samsung’s Galaxy Connect team documents `samsung-mcfcore://collectlogs` for exporting application logs on Windows. The Galaxy Book’s system log identifies Continuity Service 4.6.1327.0 before and after the four-minute call-switch recording. The six readable core and service logs contain no entries in that window. The 152 Nearby Devices log entries in the window include generic device-state events and do not identify the earbuds or an audio handoff. The export also contains a binary `.mcfetl` trace whose event contents could not be decoded. The application log export alone could not identify the switching command or transport. [Samsung support guidance](https://community.samsung.com/kr/conversations/samsung-members/4/6af36bbea7dc683896490ad2)

Both installed Windows apps contain a distinct Auto Switch request builder. In Galaxy Connect 4.6.1327.0 and Samsung Settings 8.5.7.0, `Buds.AutoSwitchRequestCommand` calls the native `BuildPacketAutoSwitchRequest` formatter. A separate method, `BluetoothClassicConnector.SetAutoSwitchPacket`, calls the settings and MDE version formatters. These are static call paths. The scan did not identify an SM-U600-specific branch or show which path ran during the call. [Windows library reader](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45877223764) · [Store version check](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45777905381)

Two public Mac implementations encode the computer handoff request with the vendor header flag clear. One documents audible phone-to-Mac switching on Buds3 Pro. The revised reader subsequently found one such request from the Galaxy Book on SM-U600. Its effect on SM-U600 audio remains unverified. The revised reader checks both flag values, reports setup messages separately, and compares incoming notifications with the reference stream-state layout. It works on the original local recording and outputs frame direction, command IDs, lengths, flag values and recognized categories. [Mac packet implementation](https://github.com/Clascheurduturfu/galaxy-continuity-mac/blob/13f0a528aaa28481460578a22853c08363d244f6/Sources/ContinuityCore/BudsProtocol.swift) · [Hardware validation](https://github.com/Clascheurduturfu/galaxy-continuity-mac/blob/13f0a528aaa28481460578a22853c08363d244f6/docs/research/validation.md) · [Formatter reference](https://github.com/alephscalioni/budsClient/blob/75ff3428ee957d28b80dfee5b387325338971f27/macOSAutoSwitch/Sources/BudsAutoSwitch/SamsungMdePacket.swift) · [Saved trace reader](https://github.com/matt-gummow/galaxy-buds-on-preview/actions/runs/45879223910)

The [Seuil Linux project](https://github.com/Eddie02345/seuil#how-it-works) documents a separate phone-to-computer Bluetooth LE channel that coordinates transfer of the audio connection. Its hardware list does not include SM-U600. A direct port also faces a macOS limitation. Seuil advertises manufacturer data, and [Core Bluetooth’s peripheral advertising API](https://developer.apple.com/documentation/corebluetooth/cbperipheralmanager/startadvertising(_:)) accepts a local name and service UUIDs. Whether the Galaxy Book and Fold also used an LE channel to coordinate with each other remains unverified.

The preview deliberately disables the [upstream MDE patch](https://github.com/timschneeb/GalaxyBudsClient/pull/729) for Buds On. Buds4 Pro executes a different application path, so ordinary Buds On reconnection failures do not establish that its firmware cannot support coexistence. Saved Samsung code distinguishes standard SPP Seamless Connection (`0xAF`), standard SPP Multipoint Status (`0x20`), and the SMEP MDE version property. A capability flag for the generic multipoint control is insufficient to rule out the MDE path. The exact SM-U600 schema and response still need validation. See the [implementation comparison](https://github.com/matt-gummow/galaxy-buds-on-preview/blob/experimental/buds-on-mac-handoff/docs/buds-on-parity.md). Factory reset, firmware operations, and generic configuration writes are also disabled.

## Protocol evidence

Analysis used Samsung’s [Galaxy Buds 9.0.10.1724 APK](https://www.apkmirror.com/apk/samsung-electronics-co-ltd/galaxy-buds/galaxy-buds-9-0-10-1724-release/galaxy-buds-9-0-10-1724-android-apk-download/#safeDownload) and the pinned GalaxyBudsClient source. Offsets below refer to the payload and start at zero.

- Validated `0x61` frames have 63-byte payloads. The EQ preset is byte 9. Byte 10 includes Answer/end call in bit 4, Decline in bit 5, and Media controls in bits 3, 2, 1, and 6. The `0x90` command preserves unrelated flags.
- Standard EQ is set with `0x86` and a preset code from 0 to 5. The `0x69` read request accepts a validated six- or seven-row, nine-band reply and displays the last row as Custom.
- The high and low nibbles of byte 11 hold the left and right hold options. The `0x92` command uses both sides, with 0 for Off and 6 for Volume. Other options and assistant subtype writes are disabled.
- The two experimental audio options use `0x85` for Gaming mode (status byte 8) and `0x6C` for Pause when one earbud is removed (status byte 46). Both are binary.
- Native and managed fixtures verify command bytes, checksums, allowed values, preservation of sibling controls, fresh status, and selected-device guards. Per-earbud volume hold, the two experimental audio options, and Custom EQ curve reading still need dedicated hardware validation.
